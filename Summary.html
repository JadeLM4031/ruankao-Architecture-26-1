🏗️五大架构风格速查

1. 数据流风格

管道-过滤器
构件（过滤器）有输入端和输出端
通过管道传递数据流
不共享状态
✅ 支持并行、高内聚低耦合
❌ 不适合交互式应用
批处理
每步处理完整数据集
前一步完全结束后才开始下一步
适合：数据转换、报表生成

2. 调用/返回风格

★ Web应用经典分层（MVC落地，案例高频）

MVC vs 三层（高频辨析）：MVC是架构模式（M=Service+DAO+Entity，V=视图，C=控制器）；三层是分层思想（表现-业务-持久）。结合：View+Controller落在表现层，Model分布在业务层+持久层。依赖原则：只能上层调下层、面向接口，不许跨层（Controller不能直接调DAO）、不许反向。案例请求流程：浏览器→Controller→Service→DAO→DB→逐层返回。
考点：分层职责（案例考"某功能放哪层"，不考框架注解）——业务规则与事务管理属于业务逻辑层（组合业务如转账=扣款+记账，要么全成功要么全回滚）；表现层只管交互不写业务（职责分离+复用）。
子风格 特点 典型应用
主程序/子程序 自顶向下调用 传统过程式编程
面向对象 封装+继承+多态 Java/C#应用
层次结构 分层，每层只与相邻层交互 TCP/IP协议栈、OSI七层

📐ATAM 架构评估核心概念

四个关键概念（必背）

概念 标准定义 判断关键词
敏感点 一个架构决策影响一个质量属性 只涉及1个质量属性，影响显著
权衡点 一个架构决策影响多个质量属性（此升彼降） 涉及≥2个质量属性
风险 架构决策存在潜在负面结果 "团队能力不足""经验欠缺""可能成为瓶颈"
非风险 经过分析，架构决策没有问题 "有效满足需求""没有负面影响"
敏感点 vs 风险陷阱："主库写入可能成为瓶颈"看似风险，但它分析的是对性能这一个属性的影响 → 是敏感点。"团队能力不足"这种组织层面不确定因素才是风险。

① 嵌入式系统分层（案例年年有一道选答）

优先级反转（嵌入式必考）：低优先级任务占着资源，高优先级任务被迫等待，中优先级任务反而先运行。解决：①优先级继承（低任务临时继承高任务优先级，尽快释放资源）②优先级天花板（访问资源时直接升到资源天花板优先级）。
实时系统分类：硬实时（时限绝对不可超：飞控、ABS防抱死）vs 软实时（偶尔超时可容忍：视频播放）。

🧩内聚与耦合

七种内聚（从低到高，功能内聚最优）

类型含义类比
偶然内聚几个功能硬凑在一起，毫无关联随机分到一组的人
逻辑内聚逻辑上相关的功能放一起，由参数决定执行哪个同一类工具放一个抽屉
时间内聚同一时间段执行的功能放一起晨起流程：刷牙洗脸穿衣
过程内聚按特定顺序执行的处理步骤放一起按步骤的菜谱
通信内聚操作同一数据集的功能放一起都操作"学生表"的增删改查
顺序内聚一个功能的输出是另一个的输入流水线：A的产出给B
功能内聚所有元素共同完成一个单一功能只做一件事且做好

七种耦合（从低到高，非直接耦合最优）

类型含义类比
非直接耦合两模块无直接关系，通过主模块间接联系互不认识，通过中间人联系
数据耦合只通过简单数据参数传递信息只传纸条不传原件
标记耦合通过数据结构（记录/对象）传递信息传整个档案袋
控制耦合传递控制信息（开关/标志），一个模块控制另一个的执行远程遥控器
外部耦合共享外部数据格式/通信协议/设备共用同一台打印机
公共耦合共享全局数据结构/公共变量共用一块白板
内容耦合一个模块直接访问另一个模块的内部数据/代码直接翻别人的抽屉
考试陷阱："传递整个数据结构"是标记耦合不是数据耦合。数据耦合只传简单参数（int、string）。传递控制标志（flag/开关）是控制耦合。

🧪白盒测试 · 逻辑覆盖

六种覆盖强度排序（从弱到强）

语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖

逐一详解

覆盖类型要求说明
语句覆盖每条语句至少执行一次最弱，只管"跑过"，连分支都可能没覆盖全
判定覆盖
（分支覆盖）		每个判定的真假分支至少执行一次覆盖了分支，但不管条件内部的各个子条件
条件覆盖每个条件的真假至少取一次管到每个子条件，但组合情况不一定覆盖
判定/条件覆盖同时满足判定覆盖和条件覆盖既覆盖分支又覆盖每个条件，但条件组合不一定全
条件组合覆盖所有条件的真假组合至少出现一次最强（除路径覆盖外），用例数最多
路径覆盖覆盖程序中所有可能的执行路径理论上最强，但路径数可能爆炸（循环导致无限路径）

快速判断技巧

  • 题目问"最弱的覆盖" → 语句覆盖
  • 题目问"保证每个条件真假都取到" → 条件覆盖
  • 题目问"所有条件组合都要覆盖" → 条件组合覆盖
  • 题目问"覆盖所有可能执行路径" → 路径覆盖
  • 条件组合覆盖的用例数 = 2^n（n=条件个数），如2个条件→4个用例
条件覆盖 ≠ 判定覆盖。条件覆盖管每个子条件的真假，但可能出现：每个条件都取过真假，但判定结果只取了真没取假。所以二者独立，判定/条件覆盖是同时满足两者。

白盒 vs 黑盒 vs 其他

类型方法关注点
白盒测试逻辑覆盖、路径分析内部代码结构
黑盒测试等价类划分、边界值分析、因果图功能是否正确，不看代码

🏭创建型模式（5种）

模式核心要点适用场景
工厂方法 定义创建对象的接口，由子类决定实例化哪个类 不知道具体要创建哪个类的实例
抽象工厂 创建一系列相关对象的接口，无需指定具体类 需要创建产品族（如跨平台UI组件）
单例 确保一个类只有一个实例+全局访问点 配置管理、线程池、日志、数据库连接池
建造者 将复杂对象的构建与表示分离，分步骤构建 对象有很多可选参数（如SQL查询构建）
原型 通过复制已有实例来创建新实例（clone） 创建成本高，复制比new更高效
单例的懒汉式=第一次使用时创建（延迟加载）；饿汉式=类加载时就创建。考试经常考反。

🏗️结构型模式（7种）

模式核心要点适用场景
适配器 将一个类的接口转换为客户端期望的另一个接口 兼容旧接口、整合第三方库
桥接 将抽象部分与实现部分分离，使它们可以独立变化 避免多层继承爆炸（如形状×颜色）
组合 将对象组合成树形结构，统一处理单个对象和组合对象 文件系统、菜单树、组织架构
装饰器 动态地为对象添加额外职责，不修改原有类 Java IO流、为对象加功能但不想改原类
外观 为子系统提供一个统一的高层接口 简化复杂子系统的调用（如一键下单）
享元 共享细粒度对象，减少内存用量 大量相似对象（如字符编辑器中的字符对象）
代理 为其他对象提供代理以控制对它的访问 远程代理、虚拟代理、保护代理、缓存代理
装饰器 vs 代理
装饰器：增强功能，不改变接口
代理：控制访问，可能改变行为
适配器 vs 桥接
适配器：事后补救，让不兼容的接口能一起工作
桥接：事前设计，将抽象与实现分离

🎯行为型模式（11种 · 高频6种）

模式核心要点适用场景
观察者 高频 一对多依赖，对象状态变化时自动通知所有观察者 事件监听、消息推送、MVC中的Model-View
策略 高频 封装算法族，使它们可以互相替换 排序算法切换、支付方式选择、折扣计算
模板方法 高频 定义算法骨架，将某些步骤延迟到子类实现 框架设计（如JUnit的setUp/tearDown）
命令 高频 将请求封装为对象，支持撤销、队列、日志 撤销/重做操作、任务队列、宏命令

⚡流水线计算

三个核心公式

时钟周期：Δt = max(各段时间)
总时间：T = (级数k + 指令数n - 1) × Δt
吞吐率：TP = n / T  |  加速比：S = 不用流水线时间 / T

计算示例

4级流水线，各段2ns/3ns/2ns/2ns，100条指令：

  • Δt = max(2,3,2,2) = 3ns
  • T = (4+100-1)×3 = 103×3 = 309ns
  • TP = 100/309 ns⁻¹
  • 不用流水线：每条9ns×100=900ns，S=900/309≈2.91

气泡（Stall）

实际时间 = 理想时间 + m×(n-1)×Δt（m=每条指令插入的气泡数）

📄LRU / FIFO / OPT 页面置换

LRU 手算方法

维护列表：左边=最近使用的，右边=最久没用的。命中→移到最左；缺页→淘汰最右，新页加最左。

三种算法对比

算法 淘汰策略 Belady异常
OPT 淘汰将来最久不用的（向后看） 不会
LRU 淘汰过去最近最久未用的（向前看） 不会
FIFO 淘汰最早进入的 可能
Belady异常 = 增加页框数反而缺页率上升。只有FIFO可能出现。LRU和OPT是栈式算法，不会。

缺页率公式

缺页率 = 缺页次数 / 总访问次数

快速判断技巧

  • 前N次访问（N=页框数）必为缺页（初始为空）
  • 刚被淘汰的页面如果马上又被访问，一定缺页
  • 序列中有连续重复的页号 → 命中机会多

🔄PV 操作

基本规则

P(S)：S=S-1，若S<0则阻塞等待  |  V(S)：S=S+1，若有等待进程则唤醒
P = 申请等待  |  V = 释放通知

生产者-消费者

缓冲区容量N。empty=N, full=0, mutex=1：

生产者：P(empty) → P(mutex) → 写 → V(mutex) → V(full)
消费者：P(full) → P(mutex) → 读 → V(mutex) → V(empty)
P的顺序不能反（先P(empty)再P(mutex)，否则死锁）。V的顺序无所谓。N=1时可省略mutex。

多读者-写者

读者：P(mutex); rc++; if(rc==1)P(rw); V(mutex); 读; P(mutex); rc--; if(rc==0)V(rw); V(mutex)
写者：P(rw); 写; V(rw)

前趋同步

P1先完成：V(S)  |  P2后开始：P(S)  |  信号量S=0

做题三问

  1. 谁等谁？ → 先完成的V，后开始的P
  2. 有没有互斥？ → 共享资源需要mutex
  3. 信号量初始值？ → 一般题目会给出

⚡Redis 缓存三大问题

雪崩 / 击穿 / 穿透 速判

问题是什么解决方案
雪崩 大量缓存同时过期，或Redis宕机，瞬间所有请求打到数据库 ① 过期时间加随机偏移（避免同时失效）
② 热点数据永不过期
③ Redis集群（高可用）
④ 限流+降级
击穿 某个热点key过期的瞬间，大量并发请求同时打到数据库 ① 互斥锁（只放一个请求去查DB）
② 热点key永不过期
③ 提前异步刷新
穿透 查询根本不存在的数据（缓存和DB都没有），每次请求都穿透到数据库 ① 布隆过滤器（前置拦截）
② 缓存空值（key→null，设短TTL）
③ 参数校验（拦截非法请求）
记忆口诀：
雪崩 = 大面积同时过期（像雪崩一样大面积坍塌）
击穿 = 一个热点key被突破（像子弹击穿靶心）
穿透 = 查不存在的数据，缓存形同虚设（直接穿透到DB）

🔥秒杀场景 + 并发控制（锁）

秒杀场景架构要点

秒杀的核心挑战：短时间内海量请求抢购有限库存，容易导致超卖、系统崩溃。解决方案分层：

层级策略说明
前端限流+防重复按钮置灰、验证码、同一用户短时间内只能提交一次
网关请求过滤Nginx限流（limit_req）、IP黑名单、只放行少量请求到后端
服务层库存预扣Redis原子操作预减库存（DECR），库存为0直接拦截，不再查数据库
数据库乐观锁/悲观锁最终落库时用锁机制防止超卖
异步消息队列削峰订单请求写入MQ异步处理，避免数据库直接承压
秒杀核心思路：拦截在前，落库在后。层层过滤，最终只有少量请求真正操作数据库。

乐观锁 vs 悲观锁

乐观锁悲观锁
思想假设不会冲突，更新时才检查假设一定冲突，先加锁再操作
实现版本号（version字段）或CAS（Compare And Swap）数据库行锁：SELECT ... FOR UPDATE
流程读数据→记版本号→修改时比较版本→版本一致则更新并+1，不一致则重试事务中先锁定行→其他事务等待→操作完释放锁
适用读多写少，冲突概率低（如秒杀）写多竞争激烈，冲突概率高（如库存扣减）
优点不锁行，并发性能好安全，不会丢失更新
缺点冲突时需重试，高并发下大量失败加锁阻塞，并发性能差，可能死锁

乐观锁防超卖 SQL 示例

UPDATE goods SET stock = stock - 1, version = version + 1
WHERE id = 1 AND stock > 0 AND version = #{当前版本号}
version不匹配则影响行数为0，说明被其他线程抢先了，需要重试。stock > 0 防止库存为负。

智能合约详解（案例300字答题模板）

智能合约是部署在区块链上的可自动执行的程序代码，由以太坊首次提出并实现。它以"如果-那么"的逻辑形式定义交易规则，当预设条件被满足时，合约自动触发执行，无需第三方中介干预。

核心特征：
（1）自动执行：条件满足即触发，无需人工干预；
（2）不可篡改：部署后代码无法修改，运行结果确定；
（3）透明公开：代码在链上可验证、可审计；
（4）去信任：不依赖第三方，由代码逻辑保证执行。

开发语言：Solidity（以太坊）、Move（Diem）等。
运行环境：EVM（以太坊虚拟机）等链上虚拟机。
应用场景：数字资产交易、供应链自动结算、保险自动理赔、DeFi借贷协议。

区块链工作流程（案例必背）

  1. 用户发起交易：用户通过钱包客户端创建一笔交易，用私钥签名
  2. 交易广播：交易通过P2P网络广播到全网节点
  3. 节点验证：各节点收到交易后验证签名有效性、余额是否充足、格式是否合法
  4. 打包进区块：矿工/验证节点将验证通过的交易打包成候选区块
  5. 共识竞争：节点通过共识机制（如PoW算力竞争、PoS权益投票）竞争出块权
  6. 区块广播与验证：获胜节点将新区块广播到全网，其他节点验证区块合法性
  7. 追加到链上：验证通过后，新区块追加到区块链末尾，交易被确认
  8. 全网同步：所有节点更新本地账本副本，达成一致性状态
流程速记：发起 → 广播 → 验证 → 打包 → 共识 → 上链 → 同步

💰挣值分析

三个基本量

符号 名称 含义

EV 挣值 到某时点实际完成的工作预算

四个偏差指标

CV = EV - AC（成本偏差）>0=节约
SV = EV - PV（进度偏差）>0=超前
CPI = EV / AC（成本绩效指数）>1=节约

EV永远是分子！"偏差"用减法，"指数"用除法

BAC = 完工总预算
EAC = BAC / CPI（典型偏差时）
ETC = EAC - AC（还需花多少）
VAC = BAC - EAC（完工偏差）

稳定性辨析（高频考点）

选择排序不稳定：例 [5, 8, 5, 2, 9]，第一趟选最小值2与第一个5交换，两个5的相对顺序改变。
快速排序不稳定：partition过程中相等元素可能被交换到不同侧。
堆排序不稳定：堆调整过程中相等元素的相对位置可能改变。
简单记忆：O(n log n)的四个算法中，只有归并排序是稳定的。

🔍各算法核心要点

冒泡排序

相邻元素两两比较，每趟把最大值"冒"到末尾。最好O(n)（已有序，一趟就停），最坏O(n²)（逆序）。

选择排序

每趟从剩余元素中选最小值放到已排序末尾。不稳定，比较次数始终为n(n-1)/2，与初始顺序无关。

插入排序

将元素插入到已排序序列的正确位置。最好O(n)（已有序），最坏O(n²)（逆序）。小规模数据或基本有序时效率高。

希尔排序

缩小增量的插入排序。先按大间隔分组做插入排序，逐步缩小间隔。平均O(n^1.3)，不稳定。

快速排序

选基准值(pivot)，partition分为左右两部分，递归排序。平均O(n log n)，最坏O(n²)（已有序+选首元素为基准）。空间O(log n)（递归栈）。

快排最坏情况：数组已有序+选第一个元素为基准→退化为O(n²)。优化：三数取中法选基准。

归并排序

分治法：拆成两半分别排序，再合并。时间始终O(n log n)（最好最坏都一样），空间O(n)（需要辅助数组）。唯一稳定的O(n log n)排序。

堆排序

建大顶堆+反复取堆顶+调整。时间始终O(n log n)，空间O(1)。不稳定。适合大数据量+空间受限场景。

基数排序

按位分配收集：从最低位到最高位，每轮用稳定排序（如计数排序）。时间O(d(n+r))，d=位数，r=基数。适合整数/字符串排序。

🎯排序算法选择（案例题考法）

场景选型

场景推荐算法理由
数据量小（n≤50）插入排序简单、常数因子小、稳定
数据基本有序插入排序最好O(n)
数据量大、随机分布快速排序平均性能最优
需要稳定排序+大数据量归并排序唯一稳定的O(n log n)
空间受限、不要求稳定堆排序O(1)空间
整数且范围不大基数排序/计数排序可达到O(n)
外部排序（数据在磁盘）归并排序顺序访问，适合磁盘IO

易混对比

快速排序 vs 归并排序
快排：先partition再递归，不稳定
归并：先递归再合并，稳定
快排空间O(log n)，归并空间O(n)
堆排序 vs 快速排序
堆排：最坏也是O(n log n)，空间O(1)
快排：最坏O(n²)，但平均更快
堆排不稳定，快排也不稳定
考试陷阱："平均性能最好的排序"→快排。"最坏情况下仍为O(n log n)"→归并/堆排。"稳定的O(n log n)排序"→只有归并。

RAG五环节（第二问，每项一段）

（1）文档解析与切分。系统首先对文档进行解析，将其切分为语义完整的片段。切分需要权衡块的大小：块过大容易引入无关内容，过小则割裂语义，因此要结合文档结构确定合适粒度，对表格、跨段落内容采用结构感知的切分方式。

（2）向量化。通过Embedding模型将每个片段映射为高维向量，语义相近的内容在向量空间中距离也更近。通用模型在专业领域的语义区分度不足，需要评估领域适配性；涉及图像的场景应选用支持图文的多模态模型。

（3）向量数据库检索。将用户提问同样向量化后，在向量库中以余弦相似度检索最相近的Top-K条片段。为在高维空间快速检索，采用HNSW等近似最近邻索引，以少量召回损失换取毫秒级响应；必要时先按元数据（如缺陷类别）过滤再检索。

（4）重排序。召回环节追求速度，重排环节追求准确：用更精细的Rerank模型对Top-K结果重新打分排序，只保留最相关的几条，构成"先粗后精"的两级检索。

（5）提示词拼接与生成。将重排后的知识片段与问题拼接成提示词，交给大模型生成答案。受上下文长度限制，需控制注入片段数量；提示中要求模型仅基于所给材料回答并标注来源，防止幻觉与提示注入。

向量库三要素（第二问）

特点：向量数据库基于语义相似度检索，而非关键字精确匹配，适合语义搜索与知识检索场景；可同时存储向量、原始内容和元数据；支持水平扩展，能支撑亿级向量。

原理：通过Embedding模型将文本、图像等非结构化数据映射为高维向量，语义相近的内容距离相近；检索时以余弦相似度找出与查询最相近的K条结果；由于精确最近邻计算代价极高，普遍采用HNSW等近似最近邻索引，以少量召回损失换取毫秒级性能。代表产品有Milvus、FAISS等。

缺点：不支持精确匹配与复杂关联查询，复杂业务需配合关系数据库使用；向量与索引的存储、内存开销较大。

端云协同

端侧部署轻量模型承担实时任务，优势是低时延、数据不出本地、可离线运行；云侧部署大模型承担复杂分析与生成，优势是算力强。模型迭代采用"云训练、端推理"分工：云端用全量数据训练并量化压缩模型，通过OTA更新推送至端侧，端侧脱敏数据回流云端持续优化。

顺序口诀：缓存异步限流降，库优拆分再扩容（缓存设计/异步处理/限流降级/数据库优化/服务拆分/水平扩容）

（1）缓存设计。采用多级缓存体系：本地缓存（Caffeine）存放热点配置与元数据，Redis分布式缓存存放巡检任务、设备状态等热点数据，影像缩略图与静态资源经CDN加速。一致性采用"先更新数据库、再删除缓存"并辅以过期时间兜底；针对雪崩对TTL做随机偏移，针对穿透缓存空结果。落地：杆塔台账、航线规划结果是典型读多写少数据，缓存命中率约九成。

（2）异步处理。将非实时链路改为消息驱动：巡检数据解析、缺陷识别结果推送、报表生成通过Kafka异步处理，削峰填谷——请求写入消息后即返回，消费端按数据库承受能力平稳消费；消费端做幂等设计防止重复处理。落地：一次巡检回传的数据包分片入队，解析服务并行消费。

（3）限流降级。网关层采用令牌桶算法限流，对单用户重复请求去重；核心链路（任务调度、缺陷告警）设置超时与熔断保护（Sentinel），下游故障时快速失败；高峰期自动降级非核心服务（统计报表、推荐），保障主链路可用性。

（4）数据库优化。读写分离分担读压力，巡检影像元数据按地市与时间维度分库分表；点云、影像等大字段存对象存储，库内只保留索引地址；持续开展慢SQL治理与索引优化，高并发写入采用批量插入；并发更新用乐观锁version字段防止重复调度。

（5）服务拆分。按业务能力将平台拆分为任务调度、航线规划、数据解析、缺陷识别、告警工单等微服务，各自独立部署、独立数据库；通过API网关统一入口，服务注册发现（Nacos）支持动态上下线。拆分带来独立伸缩与故障隔离，代价是分布式事务，采用基于消息的最终一致性方案。

（6）水平扩容。服务容器化部署（Docker+K8s），通过HPA根据CPU与消息积压指标自动扩缩容：白天巡检高峰自动扩容解析与识别服务，夜间自动缩容节省资源；数据层通过分片与多副本配合扩容。扩容后系统吞吐能力随节点数近线性提升。

项目背景
在电力行业中，输电线路的安全稳定运行直接关系到电力系统的整体可靠性。传统人工巡检方式存在效率低、安全风险高、覆盖范围有限等问题，特别是在山区、高塔及复杂地形区域，人工巡检难以满足精度与安全的要求。随着无人机技术和三维点云技术的发展，通过无人机对输电线路进行巡检成为一种高效、低风险的新模式。
然而，无人机巡检产生的数据量巨大，单次巡检可生成数十GB的点云与影像数据，且巡检任务涉及数据采集、点云解析、航线规划、缺陷识别、任务派发等多个环节，各环节之间存在复杂的数据流转和业务协同需求。传统单体架构在遇到这类海量、多模态、高并发的数据处理场景时，面临性能瓶颈、模块耦合度高、扩展困难等突出问题。为此，电力公司决定建设一个新型的无人机智能管控平台，以实现巡检业务的全流程数字化和智能化。

模块B：微服务/SOA（最通用 ⭐）
在架构选型阶段，我面临一个关键决策：采用传统单体架构还是面向服务架构？由于巡检业务涉及数据采集、点云解析、航线规划、缺陷识别、任务派发等多个环节，各环节的迭代频率和技术栈需求差异较大。例如AI缺陷识别模块需要频繁更新模型，而航线规划模块相对稳定。如果采用单体架构，任何模块的修改都需要重新部署整个系统，风险高、效率低。因此我决定采用面向服务架构（SOA），将系统按业务功能拆分为独立服务。SOA的核心原则包括：服务自治（在我的项目中，每个服务独立部署和升级，AI模块3个月迭代4个版本而不影响其他服务）、接口标准化（统一采用RESTful API，所有接口遵循/api/v1/资源名的命名规范）、松耦合（服务间通过消息队列异步通信，一方宕机不影响另一方）、服务可重用（点云解析服务可同时被巡检任务和数据分析模块调用）。微服务架构是SOA的进一步演进，强调更细粒度的服务拆分、独立的数据存储和去中心化的治理，但也引入了服务间通信、数据一致性和运维复杂度等新的挑战。结合Docker容器化和Kubernetes（K8s）编排管理，形成了云原生架构的技术基础。
适用方向：微服务、SOA、云原生、系统安全性、自动化测试、大部分通用题目（6个方向）
模块C：大数据处理
在数据架构选型时，我首先分析了项目的数据特征。无人机单次巡检可生成数十GB的点云与影像数据，日均数据量超过200GB，且包含点云、图像、结构化报告等多种数据类型。这些数据具备典型的大数据特征：Volume（日均200GB，总量已达PB级）、Velocity（巡检数据要求30分钟内完成解析）、Variety（点云、图像、日志等异构数据）、Value（海量数据中真正有价值的缺陷信息占比极低）、Veracity（传感器噪声和天气干扰影响数据质量）。面对这种数据规模，传统单机处理方式完全无法胜任。需要引入分布式存储实现大文件的分块冗余存储，采用并行计算框架将点云按空间区域分块后多节点同时处理，并通过流式计算实现实时缺陷告警。在架构设计中，需要在处理性能、存储成本和数据一致性之间做出权衡。
适用方向：大数据处理、湖仓一体、AI/智能化、数据库设计（4个方向）
模块A：分布式系统（备用）
在架构设计初期，我首先对系统的本质特征进行了分析。本系统需要同时管理多台无人机执行巡检任务，涉及航线规划、数据采集、点云解析、缺陷识别、任务派发等多个服务节点的协同工作，属于典型的分布式系统架构。其核心特征包括：节点自治性（各服务独立运行和部署）、操作透明性（用户无需感知数据分布在哪个节点）、资源共享（跨节点的存储和计算能力统一调度）。在架构设计过程中，我重点面临三大挑战：性能方面，单节点解析10GB点云需2小时，远超30分钟的业务要求，海量数据的分布式处理成为首要难题；可用性方面，巡检任务一旦开始不允许中断，任何节点故障都不能影响整体任务执行；一致性方面，点云解析完成后必须可靠地通知派发服务，消息丢失会导致巡检结果遗漏。根据CAP定理，一致性、可用性和分区容忍性三者不可兼得，需要根据业务场景做出权衡。
模块E：系统可靠性（备用）
在可靠性需求分析阶段，我首先梳理了系统故障可能带来的后果。系统可靠性直接关系到电力巡检的安全——如果巡检任务执行到一半系统崩溃，无人机可能悬停在高压线附近无法返航，存在严重的安全隐患。因此我对系统可靠性提出了明确指标：整体可用性不低于99.7%，核心服务故障恢复时间不超过30秒。可靠性设计的核心指标包括：MTTF（平均无故障时间，我要求核心服务MTTF不低于720小时）、MTTR（平均修复时间）、可用性=MTBF/(MTBF+MTTR)。在架构层面，我需要重点考虑：冗余设计（关键服务至少2个实例，消除单点故障）、故障检测（心跳机制每5秒一次，及时发现异常）、故障恢复（自动转移、熔断降级，防止级联故障）、容错设计（消息重试、补偿事务、幂等性保障，确保数据不丢失）。可靠性需要在成本和可用性之间权衡——更高的可靠性意味着更多的冗余资源和更复杂的运维。
模块F：系统自动化测试（专用）
在系统测试策略规划阶段，我首先分析了项目的测试需求特征。平台涉及点云解析、航线规划、缺陷识别等多个服务模块，服务间存在大量接口调用和数据交互，且AI模型需要频繁迭代更新，传统手工测试难以覆盖日益增长的测试场景，回归测试的工作量也随着版本迭代呈指数级增长。因此，我决定建立系统化的自动化测试体系。系统自动化测试的主要工作内容包括四个方面：一是测试框架搭建，我基于Pytest构建了统一的测试框架，支持接口测试、功能测试和性能测试的统一管理；二是测试用例设计与脚本编写，针对核心业务流程编写了自动化测试脚本，覆盖正常流程、边界条件和异常场景；三是持续集成集成，通过Jenkins Pipeline将自动化测试嵌入CI/CD流水线，每次代码提交后自动触发测试并生成报告；四是测试数据管理，建立了独立的测试数据库，通过数据工厂模式自动生成测试数据，确保测试环境的隔离性和可重复性。自动化测试的优点在于：显著提高测试效率，一次脚本编写可多次执行；减少人为遗漏和操作错误，保证测试的一致性；支持高频回归测试，在持续集成中快速发现缺陷；测试报告自动生成，便于质量度量。但其也存在不足：前期投入成本较高，框架搭建和脚本编写需要专门的时间和技术积累；不能完全替代手工测试，探索性测试和用户体验测试仍需人工完成；维护成本较高，当需求变更或接口调整时，测试脚本需要同步更新；对测试人员的技术能力要求较高，需要具备编程和自动化工具使用经验。
模块G：系统安全架构（选背 ⭐）
在系统安全需求分析阶段，我首先梳理了平台涉及的安全威胁。平台存储了杆塔坐标、巡检影像、缺陷记录等敏感数据，且服务间存在大量接口调用，面临数据泄露、越权访问、传输窃听、恶意攻击等安全风险。一旦安全防线被突破，不仅导致敏感数据泄露，更可能影响电网运行安全。因此我制定了分层安全防护策略，从四个层面构建安全体系：身份认证层，采用JWT令牌机制实现无状态认证，用户登录后颁发Token，后续请求携带Token验证身份，避免服务端Session带来的状态管理开销；传输安全层，所有服务间通信强制走TLS加密，防止中间人窃听和篡改，对外接口部署WAF防火墙过滤SQL注入、XSS等常见攻击；数据安全层，杆塔坐标、巡检结果等敏感字段采用AES-256加密后存入数据库，密钥通过配置中心统一管理，应用层无法直接接触明文密钥；访问控制层，基于RBAC模型实现权限管理，巡检员只能执行任务和查看结果，管理员可配置参数和导出报表，每个API接口都校验调用者的角色和权限。此外，我建立了审计日志机制，所有操作记录写入ELK平台，支持事后追溯和合规审查。安全架构设计需要在安全性和易用性之间权衡——过于严格的安全策略会增加用户操作负担，需要在实际项目中找到平衡点。

方案A：服务拆分与通信（通用 ⭐）
基于上述分析，我将系统按业务领域拆分为五个独立服务：点云处理服务、杆塔通道解析服务、航线规划服务、图像回传缺陷识别服务和数据流转派发服务。每个服务拥有独立的数据库和接口定义，遵循"高内聚、低耦合"原则。服务间同步通信采用RESTful API（如/api/v1/pointcloud/upload），异步通信采用RabbitMQ消息队列。选择RESTful而非gRPC，是因为团队对HTTP更熟悉，且本系统的性能瓶颈在点云计算而非服务通信。通过服务注册中心实现动态服务发现，新增节点只需注册即可加入集群。
适用：微服务、SOA、分布式、大部分题目
方案B：分布式任务调度与容错
在任务调度层面，我设计了基于调度中心的分布式任务管理方案。调度中心采用"最小负载优先"策略，根据节点CPU、内存和当前任务数进行智能分配。通过心跳机制（每5秒一次）监控节点状态，节点失联超过30秒自动触发任务迁移。关键服务部署至少2个实例，消除单点故障。数据存储采用多副本策略，保障数据可靠性。系统整体可用性达99.7%。
方案C：大数据处理架构
在数据处理层面，我设计了分层架构。原始数据层存储无人机采集的点云和影像，采用分布式文件系统实现高吞吐读写。处理层采用并行计算框架，将点云按空间区域分块分配至多节点同时处理。结果层将解析后的结构化数据存储至关系型数据库，支持业务查询和报表分析。通过消息队列连接各层，实现数据异步流转和最终一致性。
方案D：容器化部署（云原生方向用）
在部署架构层面，我将各服务以Docker容器形式打包，通过Kubernetes编排管理。每个服务拥有独立的数据库实例，通过Service实现服务间通信，避免了传统共享数据库带来的耦合问题。通过HPA机制根据CPU使用率自动调整实例数。服务更新采用滚动发布策略，新版本逐步替换旧版本，避免整体停机。容器化实现了环境一致性，消除了"在我机器上能跑"的问题。数据库同样容器化部署，利用持久卷（PV/PVC）保障数据持久化存储，主从复制实现读写分离。

故事1：点云解析性能瓶颈（通用 ⭐）
开发初期，单节点解析10GB点云文件需约2小时，远超用户期望的30分钟。我分析后发现瓶颈在单线程串行处理和频繁磁盘IO。我决定采用两个优化策略：一是引入并行计算框架，将点云按空间区域分块分配至4个节点同时解析；二是引入内存缓存减少重复IO。优化后解析时间缩短至25分钟，满足性能要求。这让我认识到架构设计必须以实际性能数据为依据，而非凭经验假设。
适用：性能、大数据、分布式、大部分题目
故事2：服务间数据不一致（通用 ⭐）
上线初期偶尔出现点云解析完成但派发服务未收到通知的情况，排查发现是消息队列高负载时消息丢失。我采取两个措施：一是消息队列开启持久化和消费确认机制；二是引入补偿任务定时扫描未同步数据并重新派发。实施后数据丢失率从0.3%降至0，任务调度成功率从98%提升至99.5%。这让我认识到分布式系统中不能假设任何通信可靠，必须设计容错和补偿机制。
适用：分布式、可靠性、数据管理、大部分题目

② SSTF / SCAN 经典序列速查（磁头53，队列98,183,37,122,14,124,65,67）

算法顺序总寻道
SSTF65→67→37→14→98→122→124→183236
SCAN(向大)65→67→98→122→124→183折返→37→14299 = (183-53)+(183-14)

SSTF关键分叉：67处选37不选98（距离30<31）。SCAN速算=|折返点-起点|+|折返点-另一端末点|。折返点=该方向最远请求（题说扫到边缘才用边缘）。SSTF缺点=可能饥饿；SCAN=电梯算法无饥饿。

③ 页面置换三条命

1. 帧未满不淘汰（装入≠淘汰）2. 命中必须刷新"最近使用" 3. OPT看将来最远（永不再用=最优淘汰），LRU看过去最远。Belady只有FIFO。

④ 流水线两公式

不等长段：ΣΔt + (n-1)×max(Δt)　|　等长段：(k+n-1)×t
周期=max(Δt)；最大吞吐率=1/周期；加速比=n×ΣΔt ÷ 总时间
流水线三连问：总时间→吞吐率→加速比，公式套就行。周期是max不是平均。

⑤ 子网块边界三步法 + CIDR两规则

①块=256-掩码末字节（.192→64 .224→32 .240→16 .248→8）②在草稿上写出边界序列 0|64|128|192 ③IP落在哪个区间→网络地址=左端、广播=右端-1
CIDR聚合：条数变前缀（2ⁿ个网络→缩短n位），起点不动窝（32个C网→/24-5=/19，起点原样保留）

⑥ 死锁资源公式（必代回验证）

保证不死锁的最少资源 = n×(m-1)+1　（n进程、每个最多m台）
反向问"最多几个进程"：n ≤ (总数-1)/(m-1)，向下取整，代回验证

⑦ PV三锚点

1. 初值=资源现有量（empty=容量、full=0、mutex=1，与进程数无关）2. 正值数资源、负值数等待（S=-2即2个等待）3. P顺序：先同步后互斥（先P(empty)再P(mutex)，反了死锁）

⑧ 等保三锚点

五级=自·指·监·强·专（三级监督保护）| 定级两要素=受侵害客体+侵害程度 | 三级及以上每年至少一测（"每半年"是1.0时代四级老规定）

⑨ 否定式选择题三步（真题每年3-5道）

①圈出"不正确/错误/不能" ②逐项标✓/✗（只判真假，不想"哪个可疑"）③选✗项——把否定式转成肯定式
错误项高发形态=张冠李戴：拿技术X的标志组件描述技术Y（B+树→关系库不是向量库；ESB→SOA不是微服务；算力竞赛→PoW不是PBFT）。

⑩ 端云/冒进/扩容对照速记

⑪ 滚动抽测新增易错（2026-10-22六轮抽测暴露）
